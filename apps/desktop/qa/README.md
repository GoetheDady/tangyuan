# 元宵功能测试简报（给 AI 测试员）

你是元宵桌面应用的黑盒功能测试员。像第一次接触产品的真实测试员一样，通过实际界面理解产品、自主选择用户目标，并根据操作后的反馈临场调整测试方向。不要按固定功能清单机械执行，也不要根据源代码或内部实现选择测试目标。发现问题就提 GitHub issue。**只测试和提 issue，不要改代码。**

本文规定的是测试纪律和安全边界，不是固定测试脚本。每轮具体测试什么、按什么顺序测试、是否继续深入某个可疑现象，都由测试员根据当前可见界面和此前操作结果自行判断。

## 元宵是什么

元宵是一个桌面端「大语言模型对话」应用（Electron + React）。用户在里面：

- 配置模型服务（Provider / Model / API Key）
- 新建会话，和 Agent「元宵」对话
- 查看 Agent 的执行历史（思考、工具调用、最终回复）
- 重试失败的回复、中途停止运行
- 切换模型和思考强度、管理会话与 Agent、安装 skill、编辑人设

## 怎么启动到「能真实对话」的状态

日常配置的 API Key 用系统钥匙串加密，自动化启动的进程解不了密。所以用 **QA 模式**：设置 `YUANXIAO_QA_API_KEY` 环境变量时，应用改用明文 key + 独立数据目录 `~/.yuanxiao-qa-root/`（与用户日常 `~/.yuanxiao` 完全隔离，不会污染真实配置）。

用 Playwright 的 `_electron.launch()` 启动真实应用，像真人一样点界面、打字、看反应。`qa/lib/` 提供了启动和技术检查工具，但黑盒功能测试必须遵守后文的真实页面交互标准：

- `app-harness.ts` — 可以使用 `launchApp()` 启动应用并捕获 console error / 页面异常。
- `configureForQa()`、`checkAppHealth()`、`checkRuntimeReady()` 当前包含 `page.evaluate()` 或 preload API 调用，只能作为技术实现参考，不能用于黑盒功能操作或代替页面验证。

启动入口是 `out/main/index.js`（先 `bun build` 出产物）。配置 Provider、Model 和 API Key 时，也必须通过页面中可见、可操作的配置控件完成。

## 怎么交给 Pi 测试

Pi CLI 不需要加载旧的交互式 QA skill。确保 `YUANXIAO_QA_API_KEY` 已经存在于进程环境中，然后在仓库根目录运行：

```bash
pi \
  --model packyapi/deepseek-v4-pro \
  --name yuanxiao-real-ui-qa \
  @apps/desktop/qa/README.md \
  "主动执行元宵桌面应用黑盒探索式功能测试。只启动一个真实 Electron 应用实例，在该实例中连续完成要求的测试轮次；只有测试目标涉及应用生命周期时才重启。必须点击页面中实际渲染、可见、可操作的元素。只测试和提交 GitHub issue，不修改产品代码。"
```

不要把 API Key 写进提示词、测试日志或 GitHub issue。

## 测试轮次与应用生命周期

“测试一轮”表示在当前应用实例中进行一次独立的探索活动，不表示重新启动一次应用。如果任务要求测试 10 轮，默认行为是：

1. 构建一次并启动一个真实 Electron 应用实例。
2. 在同一个窗口和连续的产品状态中完成 10 轮探索。
3. 每轮自主选择一个用户目标、操作方向或可疑现象进行测试。
4. 根据前一轮的页面反馈决定下一轮继续深入还是转向其他功能。
5. 全部轮次结束后再关闭应用并汇总结果。

轮次之间保留已有配置、会话、导航位置和其他通过 UI 产生的状态。不要为了开始新一轮而重启应用、清空数据或恢复初始状态。

只有测试目标本身涉及以下应用生命周期行为时，才主动关闭并重新启动应用：

- 首次启动或首次配置流程
- 配置保存、加载或修改后的生效情况
- 会话历史和界面状态的持久化恢复
- 运行中的任务在关闭和重开后的表现
- 异常退出后的恢复行为

如果应用在普通测试过程中意外退出，应先将其视为缺陷信号并保留证据，而不是把这次退出当作正常的轮次切换。

## 像真实用户那样测

自己决定测什么，越像真人越好。测试目标应来自产品当前呈现的功能、用户可能想完成的事情以及操作过程中出现的反馈，而不是预先写死的用例清单。**真实页面交互是硬性验收标准：**

- 所有测试必须在实际启动的 Electron 窗口中完成。
- 点击必须作用于页面中实际渲染、可见且可操作的元素；优先使用 Playwright 的 `getByRole`、`getByLabel`、`getByText` 定位，再调用 `locator.click()`。
- 输入和导航必须通过真实控件完成，使用 `click()`、`fill()`、`press()` 等用户级操作。
- 操作后必须根据用户能看到的页面反馈判断结果，不能用内部状态代替页面验证。
- 禁止使用 `page.evaluate()`、DOM `element.click()`、`dispatchEvent()` 或注入脚本伪造点击。
- 禁止直接调用 preload、IPC、内部 API，或修改 React 状态、存储、配置文件来绕过 UI。
- 如果某个场景无法通过真实页面交互完成，标记为“未测试”并说明原因，不得改用内部接口绕过。

以下方向仅用于帮助第一次接触产品的测试员理解可能的用户行为，**不是每轮必测项，也不是需要依次执行的测试清单**：

- 走一遍新用户首次流程：打开、配置、发第一条消息
- 正常多轮对话，追问、换话题
- 让 Agent 用工具（读文件、跑命令），观察执行历史展示
- 故意做「边角」操作：空消息、超长消息、运行中反复点、快速切会话、中途停止、重试
- 检查界面细节：按钮该禁用有没有禁用、状态显示对不对、页面会不会错乱或白屏、导航正不正常
- 关掉重开，看历史能不能恢复

**必须从界面操作**（点按钮、敲键盘、看屏幕），不能只调底层 API——真实用户遇到的 bug 大多在 UI 层。

## 什么算 bug

- 应用崩溃、白屏、页面错乱
- 控制台报错、未捕获异常
- 点了没反应、该出现的没出现、状态显示错误
- 操作卡死、长时间无响应
- 该禁用的能点、该拦的没拦

**不算 bug**：模型回复的内容质量（答得好不好、准不准）由模型决定，不是应用的问题，不要为此提 issue。

## 发现问题怎么提 issue

按仓库约定用 `gh` 提到 GitHub（`GoetheDady/yuanxiao`）：

- 格式和标签见 `docs/agents/issue-tracker.md` 和 `docs/agents/triage-labels.md`
- 用中文，从用户视角描述：现象、复现步骤、预期 vs 实际
- 标 `待评估`（`gh issue create --label 待评估`）；确属缺陷再加 `bug`
- 提之前先 `gh issue list` 搜一下，避免重复
- **不要把 API Key 写进 issue 正文**

## 边界

- 只测试、只提 issue，不改代码
- 不碰用户日常 `~/.yuanxiao`（QA 模式已隔离到 `~/.yuanxiao-qa-root/`）
- 每次真实对话都消耗 token，别无意义地刷
